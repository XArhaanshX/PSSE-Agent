2.2 Thirteen Core Pain Points
Pain 1: Manual Component Creation
Every bus, branch, transformer, load, and machine must be individually created through PSSE's data entry forms.
A 33kV double-bus substation with 6 feeders requires creation of approximately 20–40 individual bus records,
15–30 branch records, and associated transformer data. Each record requires manual entry of 5–15 fields.
Pain 2: Manual Network Modelling
The engineer must mentally translate an engineering drawing into PSSE's internal data model. PSSE uses a bus-
branch model where every component is defined by its terminal bus connections. The engineer must assign bus
numbers, track from/to bus relationships, and ensure no disconnected islands exist. This mental translation is
error-prone, especially for complex topologies.
Pain 3: Manual Topology Creation
Translating a real-world substation arrangement (e.g., breaker-and-a-half, double bus with bus coupler) into
PSSE's bus-branch model requires deep understanding of both the electrical topology and PSSE's modelling
conventions. Engineers must decide how to represent switching devices, which nodes to model explicitly, and
how to handle auxiliary buses.
Pain 4: Repetitive Substation Modelling
Utility engineers model the same substation configurations repeatedly across different projects. A standard
33/11kV distribution substation follows a well-known pattern, yet engineers recreate it from scratch every time.
There is no effective template system in PSSE for complex topologies.
Pain 5: Manual Diagram Placement
PSSE's diagram editor requires manual placement of every component on a 2D canvas. Components must be
positioned with proper spacing, alignment, and routing. There is no auto-layout feature. Engineers spend 30–
50% of total modelling time on diagram arrangement.5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD

PSSE has a steep learning curve. Junior engineers require 3–6 months to become proficient at model creation.

2.3 Why SLD Generation Is Fundamentally Difficult
Single-line diagram generation is not a trivial rendering problem. It is a constrained graph layout problem
with domain-specific aesthetic requirements:
1. Topological correctness: Every electrical conne ction must be represented as a visual conne ction. No
spurious or missing conne ctions are permissible.
2. Engineering conventions: SLDs follow strict visual conventions. Busbars are horizontal lines. Feeders
drop vertically. Transformers are positioned between voltage levels. Breakers and isolators are placed in
sequence. These conventions are culturally embedded in power engineering practice and cannot be
violated without confusing the reader.
3. Readability constraints: Components must not overlap. Conne ction lines must not cross unnecessarily.
Labels must be readable. Spacing must be uniform. These are non-trivial constraint satisfaction problems.
4. Hierarchical structure: Real substations have a natural hierarchy: voltage level → bus arrangement → bay
→ equipment chain. The SLD layout must reflect this hierarchy visually.
5. Scaling: Layout algorithms that work for 5 buses may fail catastrophically for 50 buses. The algorithm
must degrade gracefully as network size increases.
6. Aesthetic quality: Engineers are trained to read well-formatted SLDs. A poorly laid out diagram is not
merely ugly — it is functionally impaired because it obscures the topology it is meant to communicate.
2.4 Why Diagram Generation Is a Graph Problem
An SLD is a visual projection of an electrical graph G(V, E) onto a 2D plane, subject to:
V → (x, y) coordinate mapping for each electrical entity
E → polyline routing for each conne ction
Constraint set C defining minimum spacing, alignment rules, hierarchy preservation, and crossing
minimization
This is a well-studied class of problem in graph drawing literature (Sugiyama layered layout, orthogonal grid
layout, hierarchical layout). The key insight is that SLD generation is deterministic geometry constrained by
engineering conventions, not free-form artistic layout. This makes it amenable to algorithmic solution.5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD

§5. Non-Goals (Expanded Rationale)
Beyond the scope exclusion table in §4.3, the following architectural non-goals require explicit justification
because they represent common over-engineering traps:
5.1 No Vendor-Neutral Abstraction Layer
Anti-pattern: Building an abstract PowerSystemTool interface that could theoretically support PSSE,
PowerWorld, DigSilent, etc.
Why this is wrong for POC: PSSE36's API surface (psspy), data model (bus-branch), file formats (.sav/.raw), and
diagram system are deeply specific. An abstraction layer would: - Add 2–4 weeks of engineering effort for zero5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD
file:///C:/Users/arhaa/OneDrive/poc1/PRD_PSSE36_AGENTIC_AI.html 13/159immediate value - Force lowest-common-denominator API design that cannot exploit PSSE-specific features -
Create maintenance burden for an abstraction used by exactly one backend - Encourage premature
generalization before the PSSE integration is even proven
Correct approach: Build directly against PSSE36. If multi-tool support is ever needed (unlikely for 12+ months),
extract the abstraction from the working PSSE implementation.
5.2 No Kubernetes / Container Orchestration
Why: PSSE36 is a Windows desktop application with a COM/Python bridge. It cannot run in a Linux container.
The system must run on the same Windows machine where PSSE36 is installed. Container orchestration adds
zero value and substantial complexity.
5.3 No Distributed Microservices
Why: The system has one user, one PSSE instance, one execution pipeline. There is no scaling requirement. A
monolithic Python application with clean module boundaries is the correct architecture. Microservices would
add network serialization overhead, deployment complexity, and debugging difficulty for zero benefit.
5.4 No Custom LLM Training
Why: The domain vocabulary for substation description is small (~200–500 terms). Structured prompting with
few-shot examples against a frontier model (GPT-4o, Claude 3.5 Sonnet) achieves sufficient extraction accuracy.
Fine-tuning requires training data that doesn't exist yet. The correct strategy is: use structured prompting →
collect correction data from human approvals → evaluate fine-tuning need after 100+ real usage sessions.
5.5 No Real-Time Processing Requirements
Why: Model creation is a batch workflow. The engineer submits a prompt, waits for execution (seconds to low
minutes), reviews the result. There are no latency SLAs below "reasonable interactive response" (~30 seconds
for simple, ~2 minutes for complex). Do not optimize for real-time performance.

12.1 Domain Language Characteristics
Power systems engineering language is semi-structured, domain-constrained, and surprisingly regular. Key
properties:
1. Limited vocabulary: ~200–500 domain terms cover 95% of substation descriptions
2. Numeric patterns: Voltage levels (11kV, 33kV, 132kV, 220kV, 400kV), counts, ratings follow predictable
formats
3. Topology keywords: "double bus", "ring bus", "radial", "breaker-and-half", "bus coupler", "bus section"
4. Equipment nouns: "transformer", "breaker", "isolator", "feeder", "CT", "PT", "capacitor", "reactor"
5. Relationship verbs: "conne cted to", "fed from", "tapped off", "coupled with"
6. Structural patterns: "X with Y arrangement and Z feeders" is a common template
This regularity means structured extraction is highly feasible with prompt engineering alone — no fine-tuning
needed for POC.5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD

def pre_extract(prompt: str) -> dict:
    """Extract high-confidence fields deterministically before LLM."""
    hints = {}
    # Voltage extraction: "33kV", "132 kV", "33/11kV"
    voltages = re.findall(r'(\d+(?:\.\d+)?)\s*k[Vv]', prompt)
    if voltages:
        hints['voltage_levels_kv'] = [float(v) for v in voltages]
    # Equipment counts: "6 feeders", "2 transformers"
    counts = re.findall(r'(\d+)\s+(transformer|feeder|breaker|isolator|bus(?:es)?)', prompt, re.I)
    if counts:
        hints['equipment_counts'] = {eq.lower(): int(n) for n, eq in counts}
    # Topology keywords
    topo_map = {
        'double bus': 'double_bus', 'single bus': 'single_bus',
        'ring bus': 'ring_bus', 'radial': 'radial',
        'breaker and a half': 'breaker_and_half', 'mesh': 'mesh'
    }
    for keyword, topo_type in topo_map.items():
        if keyword in prompt.lower():
            hints['topology_type'] = topo_type
            break
    return hints
These deterministic hints serve as validation anchors: if the LLM output contradicts a regex-extracted voltage
level, the regex value takes precedence (higher confidence for explicit numeric patterns).

class PSSESessionManager:
    """Manages PSSE36 session lifecycle."""
    def __init__(self):
        self.is_initialized = False
        self.case_path = None
        self.bus_count = 0
    def initialize(self, max_buses: int = 500):
        """Initialize PSSE. Must be called once per process."""
        if not self.is_initialized:
            import psspy
            psspy.psseinit(buses=max_buses)
            self.is_initialized = True
    def new_case(self, sbase: float = 100.0, title: str = ""):
        """Start a fresh case. Idempotent — clears any existing case."""
        psspy.newcase_2(sbase=sbase, title1=title)
        self.bus_count = 0
        self.case_path = None
    def save(self, filepath: str):
        """Save current case to .sav file."""
        ierr = psspy.save(filepath)
        if ierr != 0:
            raise PSSEError(f"Save failed: {ierr}")
        self.case_path = filepath
    def export_raw(self, filepath: str):
        """Export current case to .raw file."""
        ierr = psspy.rawd_2(sid=0, filnam=filepath)
        if ierr != 0:
            raise PSSEError(f"Raw export failed: {ierr}")

PSSE Crash Detection:
1. Wrap every psspy call in try/except
2. Check return codes (non-zero = error)
3. Monitor PSSE process via psutil
4. If process disappears → crash detected
Recovery Procedure:
1. Log crash details (last successful action, last attempted action)
2. Wait 5 seconds for PSSE process cleanup
3. Re-import psspy (may require fresh Python process)
4. Re-initialize PSSE session
5. Replay all actions from IR up to the crashed point
6. Retry the failed action with modified parameters if applicable
7. If repeated crash → abort and report to user
POC Implementation:
- Catch exceptions → log → fail with diagnostic
- No automated restart in POC (too complex, low ROI until failure patterns understood)
Production Implementation:
- Subprocess isolation: run PSSE executor in child process
- Parent process monitors child health
- On crash: respawn child, replay from checkpoint

1. psspy.psseinit() must be called exactly once — calling it again can corrupt state
2. Bus numbers must be positive integers — no zero, no negative
3. Branch circuit IDs are strings — typically "1", "2", etc.
4. Return code 0 = success, any other value = error (but error code meanings vary by function)
5. String parameters have fixed width — bus names are typically 12 characters, padded
6. psspy functions are NOT thread-safe — never call from multiple threads
7. PSSE output goes to its own console — redirect with psspy.progress_output() and
psspy.alert_output()
8. Import order matters — import psspy before any PSSE operations, and ensure PSSE's Python path is in
sys.path
§15. Internal Representation (IR)
15.1 Why IR Is Critical
The IR is the single most important data structure in the system. It serves as:
1. Contract between agents: Intent Parser produces it, Topology Planner builds it, Validator checks it,
Layout Engine reads it, PSSE Executor consumes it.
2. Debugging artifact: When something goes wrong, the IR shows exactly what was planned.
3. Replay mechanism: Given the same IR, the executor produces identical PSSE output.
4. Retry enabler: On failure, the system retries from the IR, not from the original prompt.
5. Version history: IR versions track how the topology evolved through modifications.
Without IR, the system is a black box. Prompt goes in, PSSE model comes out, and when it fails nobody can
determine why.5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD

def build_double_bus_substation(
    bus_start: int,
    voltage_kv: float,
    feeder_count: int,
    has_bus_coupler: bool = True
) -> nx.DiGraph:
    """Build a double-bus substation topology."""
    G = nx.DiGraph()
    # Main buses
    mb1 = bus_start
    mb2 = bus_start + 1
    G.add_node(mb1, type="main_bus", base_kv=voltage_kv, name=f"MAIN-BUS-1", category="main_bus")
    G.add_node(mb2, type="main_bus", base_kv=voltage_kv, name=f"MAIN-BUS-2", category="main_bus")
    # Bus coupler
    if has_bus_coupler:
        bc = bus_start + 2
        G.add_node(bc, type="auxiliary_bus", base_kv=voltage_kv, name="COUPLER", category="internal_bus")
        G.add_edge(mb1, bc, type="breaker", branch_type="bus_coupler")
        G.add_edge(bc, mb2, type="breaker", branch_type="bus_coupler")
    # Feeder bays - distribute across both buses
    next_bus = bus_start + 10
    for i in range(feeder_count):
        fb = next_bus + i
        parent_bus = mb1 if i < feeder_count // 2 else mb2
        G.add_node(fb, type="feeder_bus", base_kv=voltage_kv, name=f"FEEDER-{i+1}", category="feeder_bus")
        # Breaker connection: main_bus → breaker → feeder_bus
        G.add_edge(parent_bus, fb, type="breaker", branch_type="breaker")
    return G5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD

ALGORITHM: HierarchicalSLDLayout
INPUT: TopologyGraph G, LayoutConfig C
OUTPUT: LayoutMap (component_id → (x, y, orientation))
Step 1: LAYER ASSIGNMENT
  - Assign each bus to a vertical layer based on voltage level
  - Highest voltage = top layer (y = 0)
  - Each lower voltage level = next layer down
  - Within same voltage: main buses on primary layer, auxiliary buses on sub-layer
Step 2: HORIZONTAL ORDERING
  - Within each layer, order buses by:
    a. Main buses first, then auxiliary
    b. Feeders ordered left-to-right by bus_number
    c. Bus coupler centered between main buses
    d. Transformers aligned with their connecting buses
Step 3: COORDINATE ASSIGNMENT
  - Bus y-coordinate = layer_index * LAYER_SPACING
  - Bus x-coordinate = position_in_layer * BUS_SPACING
  - Equipment x-coordinate = parent_bus.x (vertically aligned)
  - Equipment y-coordinate = parent_bus.y + offset_by_type
Step 4: BAY LAYOUT
  For each feeder bay:
    - Start at parent bus position
    - Stack downward: isolator (y+1), breaker (y+2), isolator (y+3), CT (y+4), feeder exit (y+5)
    - Each element at same x as parent bus connection point
Step 5: COLLISION DETECTION
  For each pair of components:
    - If bounding boxes overlap: shift right component by MIN_SPACING
    - If connection lines cross: try swapping horizontal positions
Step 6: EDGE ROUTING
  For each connection:
    - Use orthogonal routing (horizontal + vertical segments only)
    - Route around obstacles
    - Minimize total wire length
    - Minimize crossings
Step 7: FINAL ADJUSTMENT
  - Center the layout on canvas
  - Apply grid snapping (round to nearest GRID_SIZE)
  - Verify all components within canvas bounds5/22/26, 9:09 PM PSSE36 Agentic AI System - PRD

def score_layout(layout: LayoutMap, graph: TopologyGraph) -> float:
    """Score layout quality. Higher = better. Range 0.0 to 1.0."""
    overlap_penalty = count_overlaps(layout) * -0.2
    crossing_penalty = count_line_crossings(layout, graph) * -0.1
    spacing_score = evaluate_spacing_uniformity(layout) * 0.3
    symmetry_score = evaluate_symmetry(layout) * 0.2
    alignment_score = evaluate_alignment(layout) * 0.2
    bounds_score = 1.0 if all_within_canvas(layout) else 0.0
    total = (
        bounds_score * 0.1 +
        max(0, 1.0 + overlap_penalty) * 0.3 +
        max(0, 1.0 + crossing_penalty) * 0.2 +
        spacing_score +
        symmetry_score +
        alignment_score
    )
    return min(1.0, max(0.0, total))

class RetryBudget:
    max_retries_per_operation: int = 3
    max_retries_per_workflow: int = 8
    max_session_restarts: int = 1
    backoff_base_seconds: float = 1.0
    backoff_multiplier: float = 2.0
    backoff_max_seconds: float = 30.0
    def get_delay(self, attempt: int) -> float:
        delay = self.backoff_base_seconds * (self.backoff_multiplier ** attempt)
        return min(delay, self.backoff_max_seconds)

def run_pipeline(prompt: str, config: Config) -> ExecutionResult:
    session = ExecutionSession(prompt=prompt)
    try:
        session.state = "parsing"
        intent = parse_intent(prompt)
        session.state = "planning"
        graph, ir = plan_topology(intent)
        session.state = "validating"
        report = validate_topology(graph, ir)
        if report.has_errors:
            return ExecutionResult(success=False, error="Validation failed", report=report)
        session.state = "awaiting_approval"
        decision = request_approval(intent, ir, report)
        if decision.rejected:
            return ExecutionResult(success=False, error="User rejected")
        session.state = "laying_out"
        layout = compute_layout(graph, config.layout)
        session.state = "executing"
        exec_report = execute_in_psse(ir, layout, config.psse)
        session.state = "persisting"
        artifacts = persist_artifacts(session)
        session.state = "completed"
        return ExecutionResult(success=True, artifacts=artifacts)
    except Exception as e:
        session.state = "failed"
        log_failure(session, e)
        return ExecutionResult(success=False, error=str(e))

38.5 Biggest Architectural Mistake to Avoid
Going directly from natural language prompt to PSSE API calls without an intermediate representation.
This is the single most damaging architectural shortcut. Without IR: - Cannot validate before execution - Cannot
retry without re-parsing - Cannot debug what was planned vs what was executed - Cannot reproduce results -
Cannot test parsing and execution independently - Cannot evolve the system incrementally
The IR is the spine of the architecture. Every subsystem reads from or writes to the IR. Skipping it saves 2
days of implementation and costs months of debugging.
